# Camunda Russian Spell Checker v0.6.33

Плагин для Camunda Modeler 5.47.0. Назначение — помощь аналитику при создании коротких и однозначных BPMN-названий: нумерация шагов, выравнивание размеров шагов, орфография, терминология 1С/ERP и локальные рекомендации по формулировкам действий.

## Возможности текущей версии

### 1. Проверка орфографии

Проверяются короткие текстовые поля Properties Panel и подписи BPMN-элементов при прямом редактировании на canvas.

Главная кнопка `А✓ / А×` управляет именно текстовой проверкой и автоматическими текстовыми преобразованиями. В состоянии `А×` плагин:

* не запускает локальные corrections, терминологии, BPMN Naming Assistant и LanguageTool;
* не заменяет кавычки;
* не нормализует пробелы;
* команды «Проверить» и «Все» сообщают, что проверка выключена.

Ручные BPMN-команды «Нумеровать» и `↔` «Выровнять размер задач» остаются доступными, поскольку они не являются автоматической текстовой проверкой.

LanguageTool является **дополнительным** движком и по умолчанию отключён. При его отключении плагин не отправляет текст на сервер и продолжает работать на локальных правилах, терминологиях и BPMN-проверках.

### 2. Нормативные локальные рекомендации

`corrections.json` хранит локальные правила нормативного написания, независимые от LanguageTool. Например:

* `1C ERP` → `1С:ERP`;
* `1С ERP` → `1С:ERP`;
* `1CУТ` → `1С:УТ`;
* `1C:ЗУП` → `1С:ЗУП`.

При замене латинской `C` в обозначениях продуктов 1С сохраняется конкретный продукт: `1C:ЗУП` не может быть преобразован в `1С:ERP`.

Если найденный текст уже точно совпадает с нормативным вариантом, рекомендация не создаётся. Поэтому корректные `Power BI`, `Qlik Sense`, `Camunda Modeler` и аналогичные записи не предлагают заменить сами себя.

Все такие правила применяются без отдельного переключателя «Категории рекомендаций».

### 3. Автоматические «ёлочки»

Опция «Автоматически заменять кавычки на «ёлочки»» включена по умолчанию.

Парные прямые и типографские кавычки нормализуются к `«...»`. Лишние пробелы непосредственно после `«` и перед `»` удаляются.

Положение курсора сохраняется корректно при редактировании.

### 4. Нормализация пробелов

Опция «Автоматически убирать лишние пробелы» включена по умолчанию.

Во время ввода:

* одиночный пробел после слова не удаляется сразу;
* лишние пробелы между словами схлопываются после начала следующего слова;
* пробелы в начале и конце текста не удаляются агрессивно во время набора;
* запрещённые пробелы возле «ёлочек» удаляются с сохранением логичного положения курсора.

Полная нормализация выполняется при потере фокуса и при командах «Проверить» и «Все».

### 5. Терминологии

Все системные и пользовательские наборы терминов используются через единый раздел «Терминология».

Целевая структура:

    dictionary/
    ├── index.json
    ├── erp26/
    │   ├── erp26-documents.json
    │   └── erp26-catalogs.json
    └── User-custom-terms.json

`index.json` — реестр подключённых терминологий. Каждая добавленная система/терминология получает отдельную папку.

### 6. Терминология 1С:ERP 2.6

`1С:ERP 2.6` показывается для пользователя как одна системная терминология. Внутри `erp26` отдельно хранятся документы и справочники.

Системные данные основаны на предоставленных пользователем выгрузках 1С:ERP 2.6.

Для документов в «ёлочках» точным считается **только полное совпадение всего текста внутри кавычек** с названием документа. Совпадение лишь начала фразы больше не считается точным названием объекта.

Если полного совпадения нет, выполняется fuzzy-поиск по **всей фразе**, а не по произвольному фрагменту и не только по первому слову. Для документов кандидаты сначала ограничиваются одинаковым количеством слов, после чего сравнивается всё название. Поэтому опечатка в первом слове (`«Зоказ поставщику»`) корректно сопоставляется с `«Заказ поставщику»`.

Максимальное расстояние редактирования одного слова теперь настраивается в окне **Настройки → Терминология** параметром **«ERP fuzzy: максимальное расстояние редактирования одного слова»**. Диапазон — `0…5`, значение по умолчанию — `2`. Это позволяет экспериментировать на реальных схемах без изменения кода.

`0` фактически оставляет только точные ERP-названия; `1` допускает одну вставку/удаление/замену в слове; `2` — текущий рекомендуемый уровень, на котором срабатывает `«Заказ поставщикам»` → `«Заказ поставщику»`. При повышении порога сохраняется дополнительная защита: для расстояния больше `1` слово должно быть достаточно длинным и сохранять высокое посимвольное сходство. Поэтому короткое `«со»` не начинает считаться вариантом `«ОС»` даже при высоком пороге.

Суммарный бюджет правок для одного ERP-названия рассчитывается как `N + 1`, где `N` — настроенное максимальное расстояние одного слова; одновременно допускается изменение не более двух слов. Для названий длиннее двух слов по-прежнему не менее половины слов должны совпадать точно.

Если несколько ERP-объектов имеют действительно одинаковую оценку близости, плагин не выбирает один вариант произвольно, а показывает до трёх равноценных вариантов замены.

Приоритет движков фиксирован явно: **ERP/подключённая терминология → локальные corrections → BPMN Naming → LanguageTool**. Если ERP-терминология распознала ошибку во всём названии документа, пересекающаяся орфографическая рекомендация LanguageTool подавляется.

В настройках рядом с `1С:ERP 2.6` отображается диагностика загрузки словаря: количество загруженных документов и справочников либо предупреждение, если системный словарь не загрузился.

Для справочников сохраняется оконное сопоставление по токенам; допустимое расстояние изменённого слова также ограничивается параметром ERP fuzzy. Для справочников по-прежнему допускается изменение только одного слова за одно совпадение, чтобы поиск по обычному тексту оставался более консервативным, чем проверка полного названия документа в `«...»`.

### 7. Пользовательские исключения

`User-custom-terms.json` содержит слова и термины, которые не следует считать ошибками.

Пользовательские исключения имеют приоритет **над всеми движками проверки**: локальными corrections, терминологиями, BPMN Naming Assistant и LanguageTool. Если замечание целиком попадает внутрь пользовательского исключения, оно отбрасывается.

Команда «Игнорировать слово» добавляет термин именно в этот пользовательский словарь.

Список пользовательских исключений можно полностью очистить через редактор — пустой `terms` является допустимым состоянием.

Пользовательские исключения больше не дописываются во внутреннюю настройку `dictionary`, поэтому удалённый термин не должен самопроизвольно возвращаться после последующих сохранений настроек.

### 8. Добавление и управление терминологиями

В настройках доступна кнопка «Добавить терминологию».

Окно содержит:

* «Наименование»;
* «Категория»: `Справочник`, `Документы`, `Прочее`;
* большой список терминов с разделителем по строкам, `;` или `,`;
* кнопки «Отмена» и «Добавить».

После добавления создаётся отдельная папка в `dictionary/<система>/` и файл `terminology.json`; запись добавляется в `dictionary/index.json`.

Для пользовательских терминологий доступны:

* **✎ Изменить**;
* **× Удалить** с подтверждением.

Отключённую пользовательскую терминологию также можно открыть на редактирование: редактор загружает её файл напрямую и не зависит от checkbox включения.

После Add/Edit/Delete индекс и термины перечитываются до перерисовки окна настроек, поэтому список не должен отображать устаревший кэш.

Для `User-custom-terms` доступно только **✎ Изменить**. Системный набор `1С:ERP 2.6` защищён от изменения и удаления.

### 9. BPMN Naming Assistant

При прямом редактировании подписи на canvas выполняются консервативные локальные рекомендации по формулировке действия.

Основной принцип — предпочитать конкретное действие в инфинитиве. Например:

    Открывать документ «Производство без заказа»

может быть рекомендовано как:

    Открыть документ «Производство без заказа»

Начиная с v0.6.33 файл `bpmn-naming.json` является **единственным источником** глагольных правил BPMN Naming Assistant. Правила загружаются при необходимости и компилируются в lookup-map; дублирующего списка глаголов в `spellchecker.js` больше нет.

Action-рекомендации применяются только при прямом редактировании BPMN **Activity**: Task, его специализированных типов, Sub-process и Call Activity. Gateway, Event и другие не-Activity элементы не получают рекомендации вида `Открывать → Открыть`, даже если их подпись начинается таким же словом.

### 10. Автонумерация шагов

Команда «Нумеровать» автоматически нумерует действия BPMN по sequence flow.

Все сгенерированные номера шагов используют единый разделитель `:` после номера:

    01: Создать заявку
    02: Проверить заявку
    03: Отправить уведомление

**Каждый BPMN-шаг всегда получает собственный номер**, даже если названия действий полностью одинаковы:

    01: Открыть документ
    02: Открыть документ
    03: Проверить документ

Функция «Один номер шага для одинаковых действий» удалена. Сохранённое значение этой старой настройки из предыдущих версий игнорируется и не влияет на нумерацию.

Это правило действует на всех уровнях: `01:`, `08.01:`, `08.01.01:` и т. д. Старый формат с точкой (`01. Название`) распознаётся для совместимости и при следующем запуске «Нумеровать» автоматически приводится к формату с двоеточием.

#### Expanded Sub-process

Expanded Sub-process является частью **текущей схемы**, поэтому его номер полностью формирует плагин:

    08: Обработать маркированный товар

Его видимые внутренние шаги получают номер от номера этого expanded Sub-process:

    08.01: Проверить данные
    08.02: Создать документ

Существовавшая в старых версиях логика «собственного методологического номера expanded Sub-process» удалена. Если в expanded Sub-process после предыдущих версий осталось имя вида:

    08: 01.05.07 Автоматическое создание перемещения товаров

то при следующей нумерации оно мигрирует к правилу текущей схемы:

    08: Автоматическое создание перемещения товаров

#### Collapsed Sub-process

Collapsed Sub-process рассматривается как ссылка на отдельный процесс/отдельный файл. Плагин нумерует сам шаг текущей схемы, но сохраняет уже имеющийся код внешнего процесса:

    08: 01.05.07 Автоматическое создание перемещения товаров

Здесь `08:` — номер шага текущей схемы, а `01.05.07` — код внешнего процесса. Плагин не использует внешний код как префикс для внутренней нумерации и не пытается нумеровать скрытое содержимое collapsed Sub-process.

Если collapsed Sub-process расположен внутри expanded Sub-process, формат выглядит так:

    08.01: 01.05.07 Автоматическое создание перемещения товаров

Специальная задача `ШАБЛОН`, используемая как эталон для команды выравнивания размеров, **не участвует в автонумерации**: номер ей не присваивается и порядковую позицию она не занимает.

Вся одна операция «Нумеровать» записывается в историю Camunda Modeler как **единое логическое действие**. Поэтому один `Ctrl+Z` отменяет всю автонумерацию, выполненную одним нажатием, а один `Ctrl+Shift+Z` повторно применяет её целиком.

### 11. Выровнять размер задач

Команда «Выровнять размер задач» задаёт всем Task размер специальной задачи-шаблона с точным названием `ШАБЛОН` и при необходимости аккуратно освобождает место справа.

Логика поиска шаблона:

1. Сначала плагин ищет задачу `ШАБЛОН` в текущем пуле. Текущий пул определяется по выбранному элементу; если в модели только один пул, он используется как текущий.
2. Если в текущем пуле `ШАБЛОН` не найден, выполняется поиск по всей модели.
3. Поиск выполняется без учёта регистра и с нормализацией лишних пробелов, но только по самому названию задачи.
4. Если найдено несколько `ШАБЛОН` в используемой области поиска, операция не выполняется и выводится предупреждение.
5. Если `ШАБЛОН` найден в другом пуле после глобального поиска, размеры выравниваются только для Task в этом пуле. Для модели без пулов используется соответствующий BPMN Process.

Изменяются по размеру только элементы Task и их специализированные виды (`User Task`, `Service Task`, `Send Task`, `Receive Task`, `Manual Task`, `Business Rule Task`, `Script Task`). Expanded Sub-process и другие типы элементов по размеру не изменяются. Размер самого `ШАБЛОН` не меняется.

При изменении размера Task используется следующая геометрия:

* **левая граница Task остаётся на месте** — при увеличении задача растёт вправо и не заезжает на предыдущий элемент;
* при изменении высоты сохраняется вертикальный центр Task;
* Y-координаты других BPMN-элементов не меняются.

После приведения Task к размеру `ШАБЛОН` плагин проверяет горизонтальные sequence flow. Минимальный зазор задаётся настройкой «Минимальный зазор после выравнивания задач, px»; значение по умолчанию — **40 px**.

Если зазора не хватает:

* сдвигается не только ближайшая задача, а **вся последующая связанная цепочка справа**;
* перемещаются Task, Gateway, Event, Sub-process и другие BPMN-shape элементы, связанные sequence flow;
* при разветвлении сдвигаются обе ветки, при схождении используется максимальное необходимое смещение — элемент не должен уехать вправо несколько раз из-за разных веток;
* вертикальные и возвратные связи не используются как основание для горизонтального сдвига;
* расчёт выполняется отдельно на каждом уровне процесса/expanded Sub-process, чтобы дочерние элементы не перемещались дважды вместе с родительским Sub-process;
* операция идемпотентна: если размеры и зазоры уже корректны, повторное нажатие не должно продолжать раздвигать схему.

После всех resize/move плагин **заново перестраивает затронутые Sequence Flow по финальной геометрии**. Старые промежуточные waypoint-ы не используются как эталон, поэтому обычная горизонтальная цепочка остаётся прямой, а ветки строятся ортогонально без подъёма стрелок над задачами только из-за старой геометрии.

Перед изменением геометрии плагин запоминает, **с какой стороны каждого BPMN-элемента была подключена стрелка**: `LEFT`, `RIGHT`, `TOP` или `BOTTOM`. После изменения размеров и координат сохраняется эта сторона подключения, но сам маршрут строится заново. Поэтому ручной смысл компоновки не теряется: например, нижняя ветка, выходящая из Gateway снизу, после выравнивания продолжает выходить снизу; ветка, входящая в Gateway снизу, продолжает входить снизу. Для Gateway и Event точка подключения фиксируется на канонической середине выбранной стороны/вершине, чтобы стрелка не попадала на невидимую границу bounding box.

Связанные вспомогательные элементы также рассматриваются как часть визуального блока процесса. Если Task/Sub-process/Gateway/Event при выравнивании смещается, плагин анализирует связи `Association`, `DataInputAssociation` и `DataOutputAssociation`. Связанные `Text Annotation`, `Data Object Reference`, `Data Store Reference`, `Data Input` и `Data Output` перемещаются на тот же `ΔX/ΔY`, что и их процессный владелец. Это сохраняет композицию вида «шаг + документы/данные + поясняющие аннотации» после раздвигания основной цепочки.

Если вспомогательный элемент связан через Association сразу с несколькими процессными элементами:

* если все связанные процессные элементы получили одинаковое смещение, вспомогательный элемент перемещается вместе с ними;
* если связанные процессные элементы получили **разные** смещения, элемент считается общим и автоматически не перемещается — плагин не выбирает владельца произвольно;
* вложенные цепочки вспомогательных элементов обрабатываются рекурсивно через Association;
* если дочерний элемент уже переместился автоматически вместе с expanded Sub-process, плагин учитывает фактическое смещение и не двигает его второй раз.

Association не участвуют в расчёте горизонтального положения основной BPMN-цепочки: геометрию процесса по-прежнему определяют только forward Sequence Flow. Association используются только для переноса связанного визуального блока.

Если после раздвигания внутренние элементы перестают помещаться в expanded Sub-process, плагин автоматически **увеличивает ширину этого Sub-process вправо**. Сам Sub-process по-прежнему не приводится к размеру `ШАБЛОН`: изменяется только его правая граница и только настолько, насколько требуется для размещения внутренних элементов с заданным минимальным зазором. X/Y и высота Sub-process не меняются.

Расширение expanded Sub-process рассматривается так же, как увеличение Task: новая правая граница **не должна перекрывать элементы, расположенные после подпроцесса**. Поэтому сразу после расширения Sub-process он становится новым горизонтальным якорем, а вся последующая цепочка по forward Sequence Flow на том же уровне сдвигается вправо настолько, насколько нужно для восстановления минимального зазора. Сдвигаются Task, Gateway, Event, следующие Sub-process и другие BPMN-shape элементы; при разветвлении перемещаются все последующие ветки, а при схождении используется максимальное требуемое смещение. Y-координаты сохраняются.

Связанные с перемещёнными элементами Data Object / Data Store / Text Annotation также догоняют своих процессных владельцев по правилам Association. После расширения контейнера и сдвига внешней цепочки маршруты Sequence Flow перестраиваются по финальной геометрии с сохранением исходных сторон подключения.

Для вложенных expanded Sub-process расширение рассчитывается **изнутри наружу**: сначала увеличивается самый внутренний подпроцесс и при необходимости сдвигается его последующая цепочка, затем внешний подпроцесс учитывает уже итоговую геометрию вложенного уровня. Расчёт повторяется до стабилизации, поэтому внутренние элементы и связанные визуальные блоки не должны выходить за правую границу родительского Sub-process.

После этого, если итоговая схема перестаёт помещаться в Pool/Participant, плагин автоматически **увеличивает Pool и связанные Lane вправо**. Высота Pool/Lane и вертикальное расположение элементов не изменяются. Для правого поля используется тот же минимальный зазор.

Автоматическая перестройка геометрии выполняется **только** по команде `↔` «Выровнять размер задач». Обычный ввод текста и команда «Нумеровать» расположение элементов не меняют.

На панели команда отображается компактной кнопкой `↔`; полное название доступно во всплывающей подсказке.

Весь результат одного нажатия `↔` записывается в историю как **одно логическое действие**: изменение размеров Task, сдвиг последующей цепочки, перенос связанных элементов, расширение expanded Sub-process, расширение Pool/Lane и перестройка Sequence Flow отменяются одним `Ctrl+Z`. Один `Ctrl+Shift+Z` возвращает всё выравнивание целиком. Для этого плагин использует собственную внешнюю команду CommandStack, а стандартные modeling-команды выполняются внутри её `preExecute`, что позволяет diagram-js атомарно группировать их в одну операцию undo/redo.

### 12. LanguageTool

В настройках есть отдельная галочка:

    ☐ Использовать LanguageTool

По умолчанию она **отключена**.

При отключённом LanguageTool запросы к серверу не выполняются. В этом режиме также скрываются настройки источника, адреса сервера, языка проверки и задержки после ввода, поскольку они относятся только к LanguageTool.

При включении можно выбрать источник проверки:

* **Локальный сервер** — например `http://127.0.0.1:8081/v2/check`;
* **Внешний сервер** — например `https://api.languagetool.org/v2/check`.

Для каждого источника хранится отдельный адрес. В интерфейсе отображается индикатор доступности:

* серый — сервер отключён или ещё не проверен;
* жёлтый — выполняется проверка;
* зелёный — сервер доступен;
* красный — сервер недоступен.

Есть кнопка «Проверить соединение».

Автоматического перехода с локального сервера на внешний нет, поэтому включение внешней отправки происходит только явно выбранным пользователем режимом.

## Архитектура renderer-кода

В v0.6.33 начат второй этап рефакторинга. Runtime остаётся одним `spellchecker.js`, чтобы не вводить новый динамический loader и не рисковать совместимостью с Camunda Modeler 5.47.0. При этом исходник разделён по зонам ответственности в `src/renderer/` и детерминированно собирается командой:

    node tools/build-renderer.js

Такой подход позволяет постепенно уменьшать общий shared state и выносить чистые алгоритмы в изолированные модули, не меняя способ загрузки плагина в Camunda Modeler. Подробности находятся в `src/README.md`.

Пользовательские терминологии теперь кэшируются в памяти и не перечитываются с диска/через `fetch` на каждую проверку поля. Кэш инвалидируется после Add/Edit/Delete и после изменения checkbox терминологии в настройках.
